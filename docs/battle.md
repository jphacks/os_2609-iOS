# バトルの仕様

同じ地点にいる 2 人が、画面をタップして攻撃し合うリアルタイムバトル。
通信には Supabase を使う。iOS と Android が同じデータベースで対戦できるよう、**この文書の決まりを両方のアプリで守る**。

- ルールの数値の正は iOS の `ARApp/Logic/BattleEngine.swift`、テーブルと関数の正は `supabase/schema.sql`。
- どちらかを変えたら、この文書と、もう片方の OS のアプリも一緒に直す。数値が 1 つでも違うと、対戦中に 2 人の画面の HP が食い違う。

## 全体の考え方

- **ルールの計算はそれぞれの端末で行う。** サーバーは行動を受け渡すだけで、HP は計算しない。
  - 自分の行動はタップした瞬間に自分の画面へ反映し、相手に送る。
  - 相手の行動は、届いた順ではなく **相手が行った順（`seq` の順）** に反映する。
  - 2 人とも同じ行動を同じルールで計算するので、HP は同じになる。
- **勝敗だけはサーバーで確定させる。** 2 人がほぼ同時にとどめを刺すと、どちらの端末も「自分の勝ち」と計算してしまう。`finish_battle` で先に記録された勝者に両方がそろえる。
- **ログインは使わない。** プレイヤー ID はアプリを起動するたびに作るランダムな UUID。

## ルール

| 項目 | 値 | iOS での名前 |
|---|---|---|
| HP（2 人とも同じ） | 300 | `BattleEngine.maxHP` |
| 通常攻撃のダメージ | 10 | `BattleEngine.normalAttackDamage` |
| 通常攻撃のクールダウン | 0.3 秒 | `BattleEngine.normalAttackCooldown` |
| 通常攻撃 1 回で溜まる必殺技ゲージ | 10 | `BattleEngine.specialGaugeGain` |
| 必殺技ゲージの最大 | 100 | `Fighter.specialGaugeMax` |
| 必殺技のダメージ | 50 | `BattleEngine.specialAttackDamage` |

行動を 1 回反映するときの計算（`BattleEngine.apply`）。自分の行動にも相手の行動にも同じ計算を使う。

1. すでに決着がついていたら、何もしない（行動は無視する）。
2. **通常攻撃**：
   - 相手の HP を `min(10, 相手の残り HP)` 減らす。
   - 自分のゲージを 10 増やす。100 を超えたら 100 にする。
3. **必殺技**：
   - 自分のゲージが 100 未満なら、何もしない（行動は無視する）。
   - 相手の HP を `min(50, 相手の残り HP)` 減らし、自分のゲージを 0 に戻す。
4. 相手の HP が 0 になったら、行動した人の勝ち。それ以降の行動はすべて無視する。

- クールダウンは、タップした端末だけで守る。受け取った相手の行動には、クールダウンの判定をしない。
- 乱数は使わない。

## 画面の流れ

1. **ロビー**：自分のモンスターはランダムに決まる（捕まえたモンスターから選ぶ仕組みはまだない）。現在地がわかったら「〇〇で対戦相手を探す」を押せる。
2. **相手探し**：同じ地点にいる人とマッチングする。「やめる」を押すとロビーに戻る。
3. **対戦**：画面の空いている所をタップすると通常攻撃。ゲージが満タンになったら、必殺技ボタンを押せる。
4. **決着**：勝敗が確定したら結果を出す。「ロビーに戻る」で次の対戦へ。モンスターはまた選び直す。

相手がいなくなったり、通信に失敗したりしたときは、「対戦できませんでした」を出してロビーに戻る。

## Supabase とのやり取り

### 接続

- Project URL と anon key は iOS と同じものを使う（メンバーから直接受け取る。リポジトリには入っていない）。
- `service_role`（secret）の鍵は、アプリに入れない。

### テーブル

**`battles`**：対戦 1 回ぶん。アプリから直接は書き換えられない（読むだけ）。

| 列 | 型 | 内容 |
|---|---|---|
| `id` | uuid | 対戦の ID |
| `location_id` | text | 対戦する地点の ID（下の「そろえる値」を参照） |
| `status` | text | `waiting`（相手待ち）/ `playing`（対戦中）/ `finished`（終わった） |
| `player1_id` | uuid | 部屋を作った人 |
| `player1_monster` | text | 部屋を作った人のモンスター（`modelName`） |
| `player2_id` | uuid | 後から入った人。入るまでは null |
| `player2_monster` | text | 後から入った人のモンスター。入るまでは null |
| `winner_id` | uuid | 勝った人のプレイヤー ID。決着がつく前や、途中でやめた対戦は null |
| `created_at` | timestamptz | 部屋を作った時刻 |

**`battle_actions`**：各プレイヤーの行動 1 回ぶん。アプリは追加と読むことだけができる。

| 列 | 型 | 内容 |
|---|---|---|
| `battle_id` | uuid | 対戦の ID |
| `player_id` | uuid | 行動した人 |
| `seq` | int | その人の何回目の行動か。**1 から始めて、1 ずつ抜けなく増やす** |
| `action` | text | `normalAttack` か `specialAttack`。ほかの値は書き込めない |
| `created_at` | timestamptz | 書き込んだ時刻 |

主キーは `(battle_id, player_id, seq)`。

### 関数（RPC）

| 関数 | 引数 | 戻り値 | 内容 |
|---|---|---|---|
| `join_battle` | `p_location_id text`, `p_player_id uuid`, `p_monster text` | `battles` の行 | 同じ地点で待っている部屋があれば入り（`playing` になる）、なければ部屋を作る（`waiting`） |
| `finish_battle` | `p_battle_id uuid`, `p_winner_id uuid`（省略できる） | 確定した勝者の uuid（勝者なしなら null） | 対戦を `finished` にする。勝者は最初に記録されたものから変わらない |

### 1. 相手探し

1. `join_battle(地点 ID, 自分のプレイヤー ID, 自分のモンスターの modelName)` を呼ぶ。
2. 戻ってきた行の `player1_id` が自分のとき：自分が部屋を作ったので、相手を待つ。
   - Realtime で、`battles` の `id = 対戦の ID` の UPDATE を購読する。
   - 取りこぼしに備えて、2 秒ごとに `battles` の行を直接読む。
   - `player2_monster` が入ったら、相手が来た。相手は `player2_id` と `player2_monster`。
   - **110 秒**待っても来なければあきらめ、`finish_battle(対戦の ID)` を勝者なしで呼んで部屋を片付ける。
3. `player1_id` が自分でないとき：待っていた部屋に入れた。相手は `player1_id` と `player1_monster`。
4. 相手のモンスター名が知らない値なら、対戦しない（`finish_battle` を勝者なしで呼んでやめる）。

- `join_battle` は 2 分より古い部屋には入らない。待つ側があきらめる 110 秒は、それより少し短くしてある。
- 同じ地点で 2 人が同時に呼んでも、サーバーが 1 人ずつ順番に処理するので、別々の部屋で待ち続けることはない。

### 2. 自分の行動を送る

- 行動するたびに、`battle_actions` に `{battle_id, player_id: 自分, seq, action}` を書き込む。
- `seq` は対戦ごとに 1 から始め、行動するたびに 1 増やす。**画面に反映できた行動だけを送る**（クールダウン中や、ゲージ不足で無視した行動は送らない）。
- 書き込みは古い順に行う。書き込んでいる間に溜まった行動は、次にまとめて（配列で）書き込んでよい。
- 返事だけが届かなかった場合に備えて、`upsert` で `on_conflict = battle_id,player_id,seq`、重複は無視（`Prefer: resolution=ignore-duplicates`）にする。こうすると、送り直しても二重にならない。
- 失敗したら 0.5 秒待って、3 回まで試す。それでも失敗したら、相手の画面と HP が食い違うので対戦をやめる。

### 3. 相手の行動を受け取る

- Realtime で、`battle_actions` の `battle_id = 対戦の ID` の INSERT を購読する。
- 届いた行のうち、`player_id` が自分のもの、すでに反映した `seq` のもの、参加中でない対戦のものは捨てる。
- **`seq` の順に反映する。** 番号が飛んでいたら、間が届くまで後ろの行動を取っておく。
- 取りこぼしや Realtime の切断に備えて、2 秒ごとにデータベースを直接読む。
  - `battle_actions`：`battle_id = 対戦の ID`、`player_id ≠ 自分`、`seq > 最後に反映した番号` を、`seq` の順に読む。
  - `battles`：対戦の行（相手がやめていないか、決着していないかを見る）。
- 知らない `action` が届いたら、そこから先に進めないので対戦をやめる。
- 相手の行動が **60 秒**届かなければ、相手がいなくなったとみなして対戦をやめる。

### 4. 決着

- **自分の画面で決着がついたとき**（自分のとどめ、または相手のとどめを反映したとき）：
  1. 相手の行動の反映をやめる。
  2. 自分の行動を送り終えるまで待つ（とどめの行動より先に、決着が相手に届かないようにするため）。
  3. `finish_battle(対戦の ID, 自分の画面での勝者のプレイヤー ID)` を呼ぶ。
  4. **戻ってきた勝者で結果を出す。** 自分の画面での勝者と違うこともある（相手が先に記録していた場合）。
- **`battles` の `status` が `finished` になったのに気づいたとき**：
  - `winner_id` が入っていれば、相手の端末で決着がついた。残りの相手の行動をもう一度読んで反映してから、上と同じように `finish_battle` を呼び、戻ってきた勝者で結果を出す。
  - `winner_id` が null なら、相手が対戦をやめた。対戦をやめてロビーに戻る。

### 5. やめる

- 相手探しの途中や対戦中にやめるとき、または結果を見てロビーに戻るときは、`finish_battle(対戦の ID)` を勝者なしで呼ぶ。
  - 相手待ちの部屋が残らず、対戦中なら相手にも伝わる。
  - 決着がついたあとなら、記録された勝者はそのまま残る。

## 両方の OS でそろえる値

### 地点の ID（正は `ARApp/Models/Location.swift` の `Location.registered`）

違う ID を使うと、同じ場所にいても別の地点として扱われ、マッチングしない。

| `stairs` | 階段 |

### 行動

`normalAttack`（通常攻撃）、`specialAttack`（必殺技）。

### 時間

| 項目 | 値 |
|---|---|
| 相手探しをあきらめるまで | 110 秒 |
| 入らない古い部屋 | 作られてから 2 分以上（`join_battle` の中で決まっている） |
| データベースを直接読む間隔 | 2 秒 |
| 相手がいなくなったとみなすまで | 相手の行動が 60 秒届かない |
| 書き込みの再試行 | 0.5 秒あけて 3 回まで |

## 新しく作るアプリ（Android など）の確認項目

- [ ] ルールの数値と計算が、上の「ルール」と同じ
- [ ] 地点の ID とモンスターの modelName が、上の表と同じ
- [ ] `seq` を 1 から抜けなく付けて、反映できた行動だけを送っている
- [ ] 相手の行動を `seq` の順に反映している
- [ ] 決着は `finish_battle` が返した勝者で出している
- [ ] やめるときに `finish_battle` を勝者なしで呼んでいる
- [ ] iOS と対戦して、両方の画面の HP が最後まで同じになる

## 割り切っていること（ハッカソン用）

- ログインを使っていないので、anon key を持っている人なら、他人のプレイヤー ID で行動を送ることもできる。防ぐには Supabase Auth でログインさせ、RLS で自分の行だけ書けるようにする必要がある。
- 2 人がほぼ同時にとどめを刺したとき、負けになった側の画面では、結果が出る直前に相手の HP が 0 に見えることがある。
- 相手が 60 秒何もしないと、相手がいなくなったとみなされる。
